# Spec Delta

## Purpose

The catalog UI core is Tayzu's browser application. It lets a person sign in, pass
every gate the API enforces, browse the catalog of their organization per blueprint,
open an entity and its relations, and search, without any rule of its own: every
decision stays in the API. It is served from the API's own origin under a strict,
self-only Content Security Policy, and it builds the pages that `002-auth-and-rbac`,
`043-identity-lifecycle-and-org-admin` and `044-password-reset-and-account-recovery`
left to it.

## Conventions

- **Host-supplied context**: the UI never sends a `tenantId`, an organization id or an
  actor. The tenant is the session's active organization, resolved on the server.
- **Reused error codes**: this capability adds no error code. The UI renders
  `CATALOG_CONTEXT_REQUIRED`, `AUTH_FORBIDDEN`, `CATALOG_NOT_FOUND`,
  `AUTH_STEP_UP_REQUIRED`, `CATALOG_VALIDATION_FAILED`, `CATALOG_LIMIT_EXCEEDED`,
  `CATALOG_REFERENCE_VIOLATION`, `AUTH_RATE_LIMITED` and `INTERNAL` as localized messages,
  never as the server's message text.
- **Locales**: `en` and `es`. The default is the browser locale reduced to `en` or `es`,
  with `en` as the fallback; the user's choice is kept in browser storage only.
- **Page rules** (`043` Q32, `044` D14 and Q26): a page that receives a token in the URL
  fragment strips the fragment after reading it, is served with
  `Referrer-Policy: no-referrer`, loads no third-party script and never submits without a
  user action.
- **Gates**: `password_change_required`, `password_expired` and `mfa_enrolment_required`,
  as reported by `GET /v1/me`.
- **Accessibility**: WCAG 2.2 levels A and AA.

## ADDED Requirements

### Requirement: The web app is served from the API's own origin

When the deployment names a build directory, the API server MUST serve the web app from
its own origin: hashed static assets under `/assets/` with a long immutable cache, and
the app's `index.html` with `Cache-Control: no-store` for every `GET` or `HEAD` whose path
is not under `/v1`, `/api` or `/assets`, is not `/healthz` and is not one of an explicit
list of root build files, whatever characters the path holds, a dot included. The
fallback MUST NOT change the answer of any API route, of the Better Auth allowlist or of
the path-shape guard that refuses percent-encoded, double-slash and backslash paths. The
asset route MUST NOT read the file system with a client-supplied path, and the immutable
cache header of an asset MUST NOT be replaced by the default `no-store`. The fallback
MUST be rate-limited per client address. When no build directory is configured the
server MUST register no app route and answer every route as before, apart from the
security headers that every response carries. A configured directory
without `index.html` MUST fail startup with an error that names the setting and not its
value.

#### Scenario: An app path answers the app

- **GIVEN** the API is started with a build directory
- **WHEN** a browser requests `GET /catalog/service`
- **THEN** it receives the app's `index.html` with `Cache-Control: no-store`

#### Scenario: A user page with an email in its path answers the app

- **GIVEN** the API is started with a build directory
- **WHEN** a browser requests `GET /catalog/_user/alice@example.com` and `GET /catalog/service/v1.2`
- **THEN** each receives the app's `index.html`

#### Scenario: API and auth paths are unchanged

- **GIVEN** the API is started with a build directory
- **WHEN** a client requests `GET /v1/unknown`, `GET /api/auth/unlisted` and `POST /catalog/service`
- **THEN** each answers exactly as it does without the build directory

#### Scenario: A traversal attempt reaches no file

- **GIVEN** the API is started with a build directory
- **WHEN** a client requests `/assets/../index.html`, `/assets/%2e%2e/secret` or `/assets/.env`
- **THEN** each answers a 404 and no file outside the asset list is read

#### Scenario: No build directory, no app

- **GIVEN** the API is started without a build directory
- **WHEN** a browser requests `GET /`
- **THEN** it receives the same 404 as before this change

### Requirement: Every response carries a strict, self-only Content Security Policy

Every response of the API server MUST carry a Content Security Policy that allows
scripts, styles, images, fonts and connections from the app's own origin only, with no
inline script and no `eval`, and with `object-src 'none'`, `base-uri 'none'`,
`frame-ancestors 'none'` and `form-action 'self'`. A runtime style element MAY be allowed
only through a nonce that is unique per HTML response and generated by a
cryptographically secure source. Every response MUST also carry
`Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`,
`X-Content-Type-Options: nosniff`, `Cross-Origin-Opener-Policy: same-origin`,
`Cross-Origin-Resource-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp`
and a `Permissions-Policy` that disables camera, microphone, geolocation, payment and USB.
The web app MUST load no script, style, font or image from another origin. Only the
development server MAY use a looser policy, and a production build MUST NOT carry it.

#### Scenario: The app page carries the policy

- **GIVEN** the API is started with a build directory
- **WHEN** a browser requests `GET /`
- **THEN** the response carries the exact policy and headers above, and its nonce differs from that of a second request

#### Scenario: API responses carry the policy too

- **WHEN** a client requests `GET /v1/blueprints` without a session
- **THEN** the `401` response carries the same policy and headers

#### Scenario: Using the app raises no policy violation

- **GIVEN** a signed-in user
- **WHEN** they visit every page of the app in both themes
- **THEN** the browser reports no Content Security Policy violation and makes no request to another origin

### Requirement: The UI never carries the tenant, the cookie or tenant free text outside the page

The web app MUST NOT send a tenant, organization id or actor in any request, MUST NOT
read the session cookie, and MUST send `x-csrf-token: orpc` on every non-`GET` request to
the API. It MUST NOT log to the console, MUST NOT load any telemetry or logging library,
and MUST NOT store any token, password, second-factor secret, backup code, search query
or catalog data in browser storage; only the theme, the locale and an in-app return path
for the single-sign-on step-up MAY be stored. Error messages MUST be rendered from the
error code, the issue paths and counts only, never from the server's message text. A
return path, from a query parameter or from storage, MUST be accepted only if it is a
path of the app on the same origin; any other value MUST be replaced by `/`.

#### Scenario: A mutating call carries the CSRF header and no tenant

- **GIVEN** a signed-in user
- **WHEN** the app sends any non-`GET` request to the API
- **THEN** the request carries `x-csrf-token: orpc`, sends the cookie through the browser only, and has no `tenantId` field, header or parameter

#### Scenario: An internal error shows no server text

- **GIVEN** the API answers a call with `INTERNAL` and a message
- **WHEN** the app renders the failure
- **THEN** the page shows the generic localized error and not the message

#### Scenario: An external return path is ignored

- **GIVEN** the sign-in page is opened with `returnTo=//evil.example/x`
- **WHEN** the user signs in
- **THEN** the app navigates to `/`

### Requirement: The shell knows the caller's session and enforces its gates

The API MUST offer `GET /v1/me`, which reads only the caller's own session, never a bearer token, and
MUST NOT read a tenant, user or organization from its path, query or body. For a valid session it
MUST return the user's id, name and email, the active organization's id and name, the
member role, the sign-in method, whether a second factor is enrolled, and the gate that
applies: `password_expired` for an expired temporary password, `password_change_required`
for an unexpired one, `mfa_enrolment_required` for the re-enrolment marker or for an
admin or owner without an enrolled factor, or `none`. For no session, an expired or idle
session, a banned or disabled user, a tenant pending or past deletion, or a session with
no active organization, it MUST answer exactly like any other `/v1` route without a
context. A marker lookup that fails MUST fail closed. The web app MUST send a signed-out
visitor of a protected page to the sign-in page, and a gated session to its gate's page
for every route but sign-out.

#### Scenario: A member reads their session

- **GIVEN** a signed-in member with no gate
- **WHEN** the app calls `GET /v1/me`
- **THEN** it receives the member's name, organization, role `member`, sign-in method and `gate: none`

#### Scenario: A temporary password is a gate

- **GIVEN** a user signed in with an unexpired temporary password
- **WHEN** they open `/catalog/service`
- **THEN** the app shows the change-password page, and `GET /v1/me` reports `password_change_required`

#### Scenario: An admin without MFA must enrol

- **GIVEN** an admin with no enrolled factor
- **WHEN** they sign in
- **THEN** the app shows the MFA enrolment page, and `GET /v1/me` reports `mfa_enrolment_required`

#### Scenario: No session looks like any other missing context

- **WHEN** an anonymous client calls `GET /v1/me`
- **THEN** it receives the same `401 CATALOG_CONTEXT_REQUIRED` body as `GET /v1/blueprints`

#### Scenario: A machine token is not a session

- **GIVEN** a valid machine access token
- **WHEN** it calls `GET /v1/me` as a bearer token
- **THEN** it receives the same `401 CATALOG_CONTEXT_REQUIRED` body as an anonymous client

### Requirement: Users can sign in locally or with Visma Connect

The sign-in page MUST offer email and password and Visma Connect. A failed local sign-in
MUST show one message whatever the reason, and a rate-limited one MUST show when to try
again. When the account has a second factor, the page MUST ask for a TOTP code or a
backup code before the session is usable. Visma Connect sign-in MUST start only on the
user's click and MUST navigate only to an absolute `https:` URL returned by the server. A
single-sign-on failure MUST show one generic message.

#### Scenario: Local sign-in with a second factor

- **GIVEN** a user with TOTP enrolled
- **WHEN** they enter their email and password and then a valid code
- **THEN** they reach the home page with their blueprints in the sidebar

#### Scenario: A wrong password and an unknown email look the same

- **WHEN** a visitor signs in once with a wrong password and once with an unknown email
- **THEN** the page shows the same message both times

#### Scenario: Visma Connect sign-in

- **GIVEN** a user linked to Visma Connect
- **WHEN** they choose "Sign in with Visma Connect" and complete the provider's flow
- **THEN** they return signed in to the home page

### Requirement: Users can complete the temporary-password and MFA gates

The change-password page MUST change a temporary password with the current and a new
password and revoke the user's other sessions, and MUST show only the name of a failed
password rule. An expired temporary password MUST show that an administrator must act,
with sign-out. The MFA enrolment page MUST require the password, then show the TOTP
secret as a QR code and as text and the backup codes once, and MUST complete only after a
valid code. The secret and the backup codes MUST NOT be stored anywhere but the page's
own memory. Re-enrolment after an MFA reset MUST use the same page.

#### Scenario: A temporary password is changed

- **GIVEN** a user under a temporary password
- **WHEN** they enter the temporary password and a policy-compliant new password
- **THEN** the gate clears and they reach the page they asked for

#### Scenario: MFA enrolment completes only with a valid code

- **GIVEN** a user who must enrol
- **WHEN** they confirm their password, scan the code and enter a wrong code, then a valid one
- **THEN** the wrong code is refused, the valid one enrols the factor, and the gate clears

### Requirement: High-risk operations prompt for step-up

When the API answers `AUTH_STEP_UP_REQUIRED`, the app MUST open a step-up prompt chosen
from the session's sign-in method. For a Visma Connect session with a re-authorization
URL in the answer, the prompt MUST offer a Visma Connect round trip that starts only on
the user's click and stores at most an in-app return path; the API's re-authorization
callback MUST then redirect to the app's fixed step-up completion page, also when it
fails or is rate-limited, never to a location taken from the request, and the user MUST
repeat the action. For a Visma Connect session without a URL, the prompt MUST ask the
user to try again later and MUST NOT offer a code or password field. For a local session,
the prompt MUST ask for a TOTP or backup code when the user has a second factor, and for
the password otherwise, and MAY retry the original request once after a successful
verification. The server MUST log a successful Visma Connect step-up as a step-up success
with the Visma Connect method and the bound session's tenant and actor, and a failed
re-authorization callback as a re-authorization failure with its reason, with no code,
state, token or claim in either event.

#### Scenario: A local user verifies with TOTP

- **GIVEN** a signed-in user with TOTP and no fresh verification
- **WHEN** they delete an entity and enter a valid code in the prompt
- **THEN** the deletion completes

#### Scenario: A user without MFA verifies with the password

- **GIVEN** a signed-in user without a second factor
- **WHEN** they delete an entity and re-enter their password in the prompt
- **THEN** the deletion completes

#### Scenario: A Visma Connect user re-authorizes

- **GIVEN** a user signed in through Visma Connect
- **WHEN** they delete an entity, choose "Continue with Visma Connect" and complete the provider's step-up
- **THEN** they return to the entity page with a notice to repeat the action, and repeating it succeeds

#### Scenario: The callback redirect is fixed

- **GIVEN** the API is started with a build directory
- **WHEN** the re-authorization callback completes successfully, fails, or is refused by its rate limit
- **THEN** it answers `303` to `/step-up/complete`, `/step-up/complete?result=failed` or `/step-up/complete?result=rate_limited`, whatever the request carried

#### Scenario: No re-authorization is available for a Visma Connect session

- **GIVEN** a user signed in through Visma Connect whose step-up answer carries no re-authorization URL
- **WHEN** the prompt opens
- **THEN** it asks the user to try again later and offers no code or password field

#### Scenario: A Visma Connect step-up is logged

- **GIVEN** a user signed in through Visma Connect
- **WHEN** a re-authorization completes, and another callback arrives with an unknown state
- **THEN** a step-up success with method `visma_connect` and the session's tenant and actor is logged for the first, a re-authorization failure with reason `invalid_state` and no tenant for the second, and neither carries a code, state or token

### Requirement: The invitation and password-reset pages follow the page rules

The app MUST serve `/accept-invitation` and `/reset-password` at the fixed paths the
emailed links use, and `/forgot-password` to request a reset. Each link page MUST read its
identifier and token from the URL fragment, remove the fragment from the address before
any request, keep both only in memory, and submit only on the user's action. The reset
page MUST show a factor field when the confirmation answers `AUTH_STEP_UP_REQUIRED`. The
accept page MUST offer the new-account path with a password and, for an existing account,
the session path. Every rejection MUST show one uniform message. The forgot-password page
MUST show the same message for every answer but a rate limit.

#### Scenario: The reset fragment is stripped before any request

- **GIVEN** a valid reset link
- **WHEN** a user opens it
- **THEN** the address shows `/reset-password` with no fragment before the page makes any request, and no request carries the token until the user submits

#### Scenario: A reset for an MFA-enrolled user asks for the factor

- **GIVEN** a valid reset link for a user with TOTP
- **WHEN** they submit a new password without a factor
- **THEN** the page asks for a code, and submitting again with a valid code completes the reset

#### Scenario: A new invitee creates their account

- **GIVEN** a valid invitation link for an email with no account
- **WHEN** the invitee opens it, chooses a password and accepts
- **THEN** the account is created and they can sign in

#### Scenario: An invalid link shows the uniform message

- **WHEN** a visitor opens `/accept-invitation` or `/reset-password` with an unknown token
- **THEN** after they submit, the page shows the uniform invalid-or-expired message

### Requirement: The catalog table shows a blueprint's entities with sort and keyset paging

The app MUST show, for each blueprint of the tenant, a table whose columns come from the
blueprint schema (identifier, title, the spec properties in schema order, the relations
and the update time), with localized headers. It MUST page with the API's cursor, sort by
identifier, title or update time in either direction, keep the sort, order, page size and
cursor in the URL, and reset the cursor when the sort changes. Values MUST be rendered by
type; a URL value MUST become a link only for an absolute `http:` or `https:` URL, opened
with `noopener noreferrer`, and markdown MUST be rendered without raw HTML or images. An
unknown blueprint, including another tenant's, MUST show the not-found page.

#### Scenario: Sort by title and page forward

- **GIVEN** a blueprint with 120 readable entities
- **WHEN** the user sorts by title descending and moves to the next page
- **THEN** the second page continues the descending order with no gap and no repeat

#### Scenario: A dangerous URL value stays text

- **GIVEN** an entity whose `url` property holds `javascript:alert(1)`
- **WHEN** the table and the entity page show it
- **THEN** it is shown as text and is not a link

#### Scenario: Another tenant's blueprint is not found

- **GIVEN** a user of tenant `t2`
- **WHEN** they open the table URL of a blueprint that exists only in tenant `t1`
- **THEN** the app shows the not-found page

### Requirement: The entity page shows details and relations

The app MUST show an entity page with the entity's title, identifier, blueprint,
timestamps, actors, version and generation, a Details tab with the spec properties and,
when present, the status properties with their observed generation, source and time, and
a Related tab that lists forward and backward relations in the spec, status or both
scopes with cursor paging and links to each target. An entity that is missing or in
another tenant MUST show the not-found page. An entity whose identifier holds `@`, `:` or
`=` MUST open normally, with those characters sent unencoded in the app path and in the
API call. An entity whose identifier holds `/` or is made only of dots cannot be
addressed in a URL path and MUST be listed with its link disabled and an explanation.

#### Scenario: Related entities in both directions

- **GIVEN** `payments` depends on `ledger`
- **WHEN** the user opens `ledger`'s Related tab and chooses backward
- **THEN** `payments` is listed and links to its entity page

#### Scenario: An identifier with reserved characters opens

- **GIVEN** an entity `team@example.com:prod=1`
- **WHEN** the user opens it from the table
- **THEN** its entity page shows it, and no request path holds a `%`

#### Scenario: Status shown next to spec

- **GIVEN** an entity with status written by an integration
- **WHEN** the user opens its Details tab
- **THEN** the status properties are shown with their observed generation and source

### Requirement: Users can search the catalog from anywhere

The app MUST open a search dialog with `Ctrl`+`K` or `Cmd`+`K` and from the header,
listing matching blueprints and, once the query has at least two characters, matching
entities from the server's search, with keyboard navigation. A newer query MUST cancel
the older request so that a stale answer is never shown. A search page MUST show the
full result list for a query kept in the URL. The query MUST NOT be stored in browser
storage.

#### Scenario: Search by identifier prefix from the keyboard

- **GIVEN** a signed-in user and an entity `payments-api`
- **WHEN** they press `Ctrl`+`K`, type `paym` and press `Enter` on the first entity result
- **THEN** the entity page of `payments-api` opens

#### Scenario: Search never shows another tenant's entity

- **GIVEN** an entity `secret-svc` in tenant `t1` only
- **WHEN** a user of tenant `t2` searches for `secret`
- **THEN** no result is shown

### Requirement: The app is localized and themed

The app MUST offer `en` and `es` for every text it owns, choose the locale as the
Conventions state, let the user change it, and set the document language. Blueprint and
property titles MUST use the active locale with `en` as the fallback. Dates MUST be shown
in the browser's time zone. The app MUST offer a light theme, a dark theme and the system
preference, apply the stored choice before the first paint without inline script, and
keep working when browser storage is unavailable.

#### Scenario: Spanish browser, no choice stored

- **GIVEN** a browser whose language is `es-AR` and no stored choice
- **WHEN** the user opens the app
- **THEN** the app is in Spanish and the document language is `es`

#### Scenario: Storage unavailable

- **GIVEN** a browser whose storage throws on every access
- **WHEN** the user opens the app and changes the theme
- **THEN** the app works and the theme changes for the session

### Requirement: The app meets WCAG 2.2 A and AA

Every page of the app MUST be operable by keyboard alone, MUST have labelled controls and
landmarks, and MUST pass an automated WCAG 2.2 A and AA check with no violation in both
the light and the dark theme.

#### Scenario: No accessibility violation on any page

- **GIVEN** the e2e stack with seeded data
- **WHEN** the accessibility check runs on every page in both themes
- **THEN** it reports no violation

### Requirement: The web app adds no browser telemetry and the server's new signals carry no tenant free text

The web app MUST NOT emit telemetry of any kind. The server MUST declare in its telemetry
contract the span of `GET /v1/me` with its gate attribute, and MUST export every HTTP
server span whose path is not under `/v1`, `/api` or `/assets`, is not `/healthz` and is
not a root build file as one fixed template, at any status and for any method, so that no
blueprint or entity identifier from an app path reaches an exported span, whether or not
the app answered the request. An organization name, a user name or an email MUST NOT
reach any signal.

#### Scenario: App paths are exported as one template

- **GIVEN** a browser that opens `/catalog/_user/someone`
- **WHEN** the HTTP server span is exported
- **THEN** its path attributes hold the fixed app template and not the path

#### Scenario: Refused and non-GET app paths are exported as the template too

- **WHEN** a client sends `POST /catalog/_user/alice@example.com`, and `GET /catalog/_user/a%40b.com`, which the path guard refuses
- **THEN** both exported HTTP server spans hold the fixed app template and no email
