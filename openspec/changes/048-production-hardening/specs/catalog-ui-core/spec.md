## ADDED Requirements

### Requirement: Content Security Policy violation reports are counted without their content

The server MUST accept browser violation reports at `POST /v1/csp-reports`, a public route on
the reviewed public-route list that reads no session, in both the `application/csp-report`
format and the `application/reports+json` format; those two media types MUST be the only
non-JSON bodies this route accepts. It MUST answer `204` with no body to every report it
accepts, whether the body is well formed, malformed or larger than its 8 KiB limit, and
whether or not the caller's address is over its per-address budget. It MUST parse a body
into null-prototype objects, refusing `__proto__`, `constructor` and `prototype` at every
depth, check the size limit before parsing, and read only the effective or violated
directive of each report, never its document, blocked or source URL, sample, referrer,
status, disposition or any other field. Each report MUST increment the
`tayzu.web.csp_violations` counter once, with its directive mapped onto the policy's own
directive names (a level-3 sub-directive such as `script-src-elem` counted under the
directive it falls back to) or onto the fixed value `other`; a report over the budget, or
with no readable directive, MUST be dropped without being counted. The route MUST write no
log record per report. The count MUST be treated as untrusted: anyone can send a report.

#### Scenario: A report is counted by its directive only

- **WHEN** a browser posts a `csp-report` whose `effective-directive` is `script-src-elem` and whose `document-uri`, `blocked-uri` and `script-sample` hold a marker string
- **THEN** the answer is `204`, `tayzu.web.csp_violations` is incremented once with the directive `script-src`, and the marker appears in no exported span, metric or log attribute and in no log record

#### Scenario: A Reporting API batch is counted per violation

- **WHEN** a browser posts an `application/reports+json` array with two `csp-violation` reports and one report of another type
- **THEN** the answer is `204` and the counter is incremented twice, once per violation's directive

#### Scenario: An unknown directive is counted as other

- **WHEN** a report names a directive that is not in the policy
- **THEN** the counter is incremented with the directive `other`

#### Scenario: A malformed, hostile or oversized report still answers 204

- **WHEN** a report is not JSON, holds a `__proto__`, `constructor` or `prototype` key at any depth, or exceeds 8 KiB
- **THEN** the answer is `204`, nothing is counted, and no internal error is logged

#### Scenario: Other media types are refused like any `/v1` body

- **WHEN** a client posts `application/json` or `text/plain` to `/v1/csp-reports`
- **THEN** the answer is the same `415` as for any other non-JSON body under `/v1`, and nothing is counted

#### Scenario: A flood from one address is dropped

- **WHEN** one address sends more reports than its per-address budget
- **THEN** every answer is still `204`, and only the reports within the budget are counted

#### Scenario: The report route is public and reads no session

- **WHEN** the reviewed public-route list and the route are checked
- **THEN** `POST /v1/csp-reports` is on the list with its reason, and a request with a session cookie is counted the same way as one without

## MODIFIED Requirements

### Requirement: Every response carries a strict, self-only Content Security Policy

Every response of the API server MUST carry a Content Security Policy that allows
scripts, styles, images, fonts and connections from the app's own origin only, with no
inline script and no `eval`, and with `object-src 'none'`, `base-uri 'none'`,
`frame-ancestors 'none'` and `form-action 'self'`. A runtime style element MAY be allowed
only through a nonce that is unique per HTML response and generated by a
cryptographically secure source. Every response MUST also carry
`Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`,
`X-Content-Type-Options: nosniff`, `Cross-Origin-Opener-Policy: same-origin`,
`Cross-Origin-Resource-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp`
and a `Permissions-Policy` that disables camera, microphone, geolocation, payment and USB.
The policy MUST name the app's own same-origin violation report endpoint, through both
`report-uri` and `report-to`, and every response MUST carry a `Reporting-Endpoints` header
that maps the `report-to` name to that same-origin path; no report MUST go to another origin.
The web app MUST load no script, style, font or image from another origin. Only the
development server MAY use a looser policy, and a production build MUST NOT carry it.

#### Scenario: The app page carries the policy

- **GIVEN** the API is started with a build directory
- **WHEN** a browser requests `GET /`
- **THEN** the response carries the exact policy and headers above, and its nonce differs from that of a second request

#### Scenario: API responses carry the policy too

- **WHEN** a client requests `GET /v1/blueprints` without a session
- **THEN** the `401` response carries the same policy and headers

#### Scenario: Using the app raises no policy violation

- **GIVEN** a signed-in user
- **WHEN** they visit every page of the app in both themes
- **THEN** the browser reports no Content Security Policy violation and makes no request to another origin

#### Scenario: The policy reports violations to the app's own origin

- **WHEN** a client requests `GET /` and `GET /v1/blueprints`
- **THEN** both policies carry `report-uri /v1/csp-reports` and `report-to` with the endpoint name of the `Reporting-Endpoints` header, which names the path `/v1/csp-reports` on the app's own origin

### Requirement: The web app adds no browser telemetry and the server's new signals carry no tenant free text

The web app MUST NOT emit telemetry of any kind; the violation reports a browser sends on its
own under the Content Security Policy are not the app's telemetry, and the server MUST reduce
each one to a directive name before any signal. The server MUST declare in its telemetry
contract the span of `GET /v1/me` with its gate attribute and the counter of Content Security
Policy violations with its directive attribute, and MUST export every HTTP
server span whose path is not under `/v1`, `/api` or `/assets`, is not `/healthz` and is
not a root build file as one fixed template, at any status and for any method, so that no
blueprint or entity identifier from an app path reaches an exported span, whether or not
the app answered the request. An organization name, a user name or an email MUST NOT
reach any signal.

#### Scenario: App paths are exported as one template

- **GIVEN** a browser that opens `/catalog/_user/someone`
- **WHEN** the HTTP server span is exported
- **THEN** its path attributes hold the fixed app template and not the path

#### Scenario: Refused and non-GET app paths are exported as the template too

- **WHEN** a client sends `POST /catalog/_user/alice@example.com`, and `GET /catalog/_user/a%40b.com`, which the path guard refuses
- **THEN** both exported HTTP server spans hold the fixed app template and no email
