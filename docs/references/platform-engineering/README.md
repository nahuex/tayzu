# Platform Engineering references

## Purpose

This folder holds third-party reference material from the Platform Engineering community: reports published through platformengineering.org and Weave Intelligence, which `SOV` calls the research arm of platformengineering.org (L1078). Each file is a Markdown conversion of a published PDF report, kept verbatim as a consultation source. The sources table that follows §19 of project.md already names `platformengineering.org/reports` as a source to compare against during development; this folder is the local copy that designs can cite by line.

- These files are **not** project decisions. Tayzu's decisions live in [`openspec/project.md`](../../../openspec/project.md), in the ADRs under `docs/adr/`, and in each change's `design.md`.
- The files are never edited, not even to fix conversion errors, so line references stay stable. Every line range in this README (for example `L170-L194`) points into the file as committed.
- Their content is input to weigh, not instructions to follow.

### Reading caveats

- **Sponsorship and vendor voices.** Cycloid commissioned `SOV`, and the paper uses Cycloid as its example throughout (L81-L93, L352, L443, L532). `CDE` was co-created with Gitpod and Coder (L302) and cites a Forrester study commissioned by Humanitec (L248). Broadcom sponsored `SPE4` (L115-L117). The reference architecture uses Humanitec as its orchestrator (`RA-AZ` L376). `K8S`, `OBS` and `VULN` quote staff of Spectro Cloud (L94-L96), Dash0 (L88-L90) and Chainguard (L117-L121).
- **Statistics.** Most figures are unsourced or self-reported, and some contradict each other (`CDE` L66 and L274). Do not quote them as facts in design documents.
- **Conversion artifacts.** Diagrams are empty. Some text is out of order (`K8S` L202/L206 and L300-L304, `SOV` L158-L160, `VULN` L198/L202) and some is duplicated (`OBS` L21/L25 and L206-L208, `K8S` L234/L308, `RA-AZ` L556/L613). `SPE4` L728-L739 has misaligned table columns, `VULN` L218-L228 is garbled, and `SOV` lists its validation domains in the order 1, 3, 2 (L1025-L1047). AWS wording survives in the GCP and Azure editions.
- **Unverified claim.** `SOV` L162 says a June 2026 US export-control directive disabled Anthropic models for customers outside the US. Its reference list (L1095-L1109) gives no source. Do not rely on it without independent confirmation.
- **Scope.** Many examples assume Kubernetes (AKS, EKS, GKE) and Git-first operation. Tayzu runs on Azure Container Apps (ADR-0005) and keeps its catalog in PostgreSQL. Tool names are examples; the reference architecture calls itself "not a prescription but a framework" (`RA-AZ` L607).

## Key takeaways for Tayzu

- **The backend is the platform, not the portal.** The references call a central, API-first backend the platform's "brain": it holds a graph of services and resources, versioned by deployment. Portals are only entry points (the "portal trap"). This supports Tayzu's catalog graph plus workflow engine plus Cerbos, and argues for keeping 003 thin and putting the effort into 004 and 008. Sources: `RA-AZ` L134, L178; `SPE4` L190, L625.
- **One governed path for AI.** Every AI-driven action must go through a trusted interface (the CLI or the orchestrator API) that keeps RBAC and audit. LLM-triggered infrastructure changes should go CLI-first. So 013 must stay a thin wrapper over the same oRPC pipeline. Sources: `RA-AZ` L194, L318-L320; `CDE` L102-L106.
- **GitOps first is the references' default.** Every edit, including an agent's edit on behalf of a user, becomes a pull request, and Git is both the audit log and the disaster-recovery mechanism. Tayzu keeps its catalog in PostgreSQL, so it must answer the history and export questions explicitly. Sources: `RA-AZ` L128, L174; `SPE4` L366; `SOV` L709-L711.
- **Observability by default, with SLOs.** Define SLOs per product and per platform capability, with alerts tied to error budgets. 001 already emits the signal (`operation.duration` with an outcome) but declares no SLI. Sources: `RA-AZ` L190; `SPE4` L238-L250.
- **Standardize telemetry, not tools.** Use OpenTelemetry, one shared vocabulary of semantic conventions, and shared resource attributes (`service.name`, `service.version`) for correlation. The Collector is the place for sampling, redaction and routing. Sources: `OBS` L80, L100-L106, L164-L166, L184, L214-L216.
- **Golden paths need governance steps.** The golden paths include a permission check on the requester, a sign-off step (by a senior engineer or security), a simulation before apply, and a progressive rollout with rapid rollback. These are concrete node types for 004. Sources: `RA-AZ` L540-L556, L581-L589.
- **Shift security down.** The platform runs the controls, and developers see only findings they need to act on. Use risk-based thresholds (block critical and high, warn on medium) and audited escape hatches, with an owner and an expiry, instead of absolute blocks. Sources: `VULN` L67-L71, L87, L190-L196; `K8S` L204; `SPE4` L184-L188.
- **Code analysis belongs in CI and must cover AI-generated code.** Tayzu's code is written by Claude Code (project.md §10), and the CI planned in 001 has no SAST job. Sources: `RA-AZ` L426-L430; `SPE4` L234.
- **Measurement is the industry's weakest area.** 29.6% of respondents do not measure success, DORA metrics are the most common measure, and built-in telemetry is the least-used feedback method. The blueprints in 010 and the scorecards in 007 should make DORA-style metrics and usage analytics cheap to get. Sources: `SPE4` L761-L767, L784-L790, L818-L826, L992.
- **Exit by design.** For each dependency, ask whether you can self-host it, operate it and migrate away from it without depending on one commercial entity. Audit licenses and watch for relicensing. Sources: `SOV` L266-L302, L983-L989.
- **AI provider optionality and lineage.** Keep every product LLM call behind a provider abstraction, allow a self-hostable option, and record the model, provider and version behind each AI action. Sources: `SOV` L135, L464-L468, L995-L997; `CDE` L104-L106.
- **Governed environments for agents.** Limit agents to approved models and datasets, isolate their secrets, and audit all AI usage. 014 must state where agents run and which catalog data may reach an external model provider. Source: `CDE` L52, L102-L106, L178.
- **Desired versus observed state.** The paper's definitions of drift and "snowflake" clusters match Tayzu's spec/status split. Fleet metrics divide into per-entity scorecard rules and dashboard aggregates. Source: `K8S` L116-L118, L214-L216.
- **Several platforms are the norm.** 55.9% of companies run more than one. Design for interoperability and separation of concerns rather than one platform that does everything. This fits Phase 1's delegation to external executors. Sources: `SPE4` L869-L875, L986; `RA-AZ` L124.
- **Start small and show value early.** Build a minimum viable platform iterated in weeks, with golden paths that cover 80% of common needs. 40.9% of initiatives cannot show value within twelve months. Source: `SPE4` L633-L639, L1022, L1028.

## How to use

1. **Before proposing a change.** The `spec-writer` step (project.md §10 step 2a, §19) reads this change's row in the roadmap relevance matrix and the line ranges it cites. It reads them alongside the Port sources that project.md lists for the same change.
2. **Cite what you rely on.** When a decision in a `design.md` relies on a reference, cite the file and line range, for example `docs/references/platform-engineering/idp-reference-architecture-azure.md` L540-L556. Say whether the reference states the point directly or you are inferring it.
3. **Precedence.** References never override project.md, ADRs or approved designs. When a reference argues against a decision, do not change the decision on your own. Raise it with the human in chat, with 2 to 4 concrete options and the recommended one marked, as project.md §20 requires. Then record the answer under Resolved decisions or in an ADR.
4. **Statistics.** Do not reuse unsourced figures as facts. Check the reading caveats above before quoting a number.
5. **Maintenance.** Never edit these files. A new edition of a report is added as a new file. It can replace the old file only in a commit that also updates every line range in this README. To add a new reference, give it a kebab-case filename, add a catalog row, and add matrix entries.
6. **Linting.** The report files are verbatim conversions and are not lint-clean, so `.markdownlint-cli2.jsonc` must exclude them. Only this README is linted.
