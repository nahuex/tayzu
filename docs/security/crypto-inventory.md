# Cryptographic inventory

SSA section SEC05, for `002-auth-and-rbac`. Every algorithm the system uses,
and where. It is read from the code and from the installed library sources
(`better-auth@1.7.6`, `@better-auth/api-key@1.7.6`, `@better-auth/utils@0.4.2`),
not from the design. Tayzu writes no cipher of its own: anything Better Auth
provides is used as configured, and the only primitives `@tayzu/auth` and
`apps/api` call from `node:crypto` are listed below. The keys and secrets
involved are in [Secrets](secrets.md).

| Purpose                                          | Algorithm                                                                                    | Where                                                                                                                                                                                                                                               |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Password hashing                                 | `scrypt` (`node:crypto`), `N=16384`, `r=16`, `p=1`, 64-byte key, random 16-byte salt         | Better Auth's `emailAndPassword` default, through `@better-auth/utils/password`. Stored as `salt:key`. Not overridden in `packages/auth/src/auth.ts`.                                                                                               |
| Machine credential secret hashing                | SHA-256, base64url, unsalted                                                                 | `@better-auth/api-key` `defaultKeyHasher`; `disableKeyHashing` is left at its default `false`. The secret is high entropy and shown once, so it is looked up by its hash.                                                                           |
| Rate-limit bucket keys                           | SHA-256 of `scope:kind:value`, hex                                                           | `packages/auth/src/rate-limit/pre-auth-rate-limit.ts`, so no IP address or email is stored in clear in `auth.rate_limit`.                                                                                                                           |
| Session cookie signature                         | HMAC-SHA-256 with `BETTER_AUTH_SECRET`, base64                                               | Better Auth's signed cookie format. `pre-auth-rate-limit.ts` recomputes it with `createHmac('sha256', ...)` and compares with `timingSafeEqual` to resolve the session user.                                                                        |
| Machine access token signature                   | `EdDSA` over Ed25519 (`jose`)                                                                | The `jwt` plugin, configured in `auth.ts` with no `keyPairConfig`, so its default applies. Issuer and audience are the fixed `tayzu-auth`. Verified in-process with `verifyJWT`. The public keys are served at `GET /api/auth/jwks`.                |
| Machine access token lifetime                    | 1 hour (`exp` claim)                                                                         | `packages/auth/src/token-exchange.ts`.                                                                                                                                                                                                              |
| `jwt` private key at rest                        | XChaCha20-Poly1305 with a random nonce, key = SHA-256 of `BETTER_AUTH_SECRET`                | Better Auth's `symmetricEncrypt`; `disablePrivateKeyEncryption` is not set. Stored in the `auth.jwks` table.                                                                                                                                        |
| TOTP secrets and backup codes at rest            | The same XChaCha20-Poly1305 `symmetricEncrypt`                                               | The `two-factor` plugin. Backup codes use `storeBackupCodes: "encrypted"`, its default. Neither is configured in `auth.ts`.                                                                                                                         |
| TOTP codes                                       | HMAC-SHA-1, 6 digits, 30-second period (RFC 6238)                                            | The `two-factor` plugin's `createOTP` from `@better-auth/utils/otp`, with no hash override. SHA-1 is the algorithm authenticator apps expect, and is safe in HMAC use.                                                                              |
| OAuth tokens from Visma Connect at rest          | The same XChaCha20-Poly1305 `symmetricEncrypt`                                               | `account.encryptOAuthTokens: true` covers the access and refresh tokens. `auth.ts` encrypts the ID token with `setTokenUtil`, the same primitive, before it is stored (task 23.19).                                                                 |
| Visma Connect ID token verification (sign-in)    | Signature check against the provider's discovered JWKS                                       | Better Auth's `genericOAuth` with `requireIdTokenVerification: true`. Tayzu does not choose the algorithm.                                                                                                                                          |
| Visma Connect logout and re-authorization tokens | `RS256` (RSA PKCS#1 v1.5 with SHA-256), key selected by `kid` from the discovered JWKS       | Hand-written checks over `node:crypto` `createVerify('RSA-SHA256')` in `packages/auth/src/sso/backchannel-logout.ts` and `sso/reauthorization.ts`. Any other `alg` is rejected. A hardening change with `jose` is a recorded residual risk.         |
| OAuth authorization code protection              | PKCE `S256` (SHA-256, base64url), `state`, `nonce`                                           | Sign-in: `pkce: true` in `sso/visma-connect.ts`. Step-up re-authorization: `apps/api/src/reauthorization.ts` with `randomBytes` for the verifier and `state`.                                                                                       |
| Random identifiers and one-time values           | `node:crypto` `randomBytes` and `randomUUID`                                                 | Re-authorization `state` and PKCE verifier, replay and verification row ids, and the single-use temporary password of `identity.users.create` (24 random bytes).                                                                                    |
| PostgreSQL connections                           | TLS with `sslmode=verify-full`                                                               | `createPool` (`packages/db/src/connection-security.ts`) refuses any other mode outside the test harness, for both `DATABASE_URL` and `AUTH_DATABASE_URL`. The harness may skip TLS only for `localhost`, `127.0.0.1` and `::1`.                     |
| Cerbos PDP connection                            | gRPC over TLS, except loopback                                                               | `apps/api/src/server.ts` turns TLS on unless `CERBOS_ADDRESS` matches `localhost`, `127.0.0.1` or `[::1]` with a port. Certificate verification is whatever `@cerbos/grpc` does with `tls: true`; Tayzu passes no custom CA or verification option. |
| Outbound HTTPS to Visma Connect                  | TLS, `https` required                                                                        | `VISMA_CONNECT_DISCOVERY_URL` must be `https` outside test. Node's default certificate verification applies.                                                                                                                                        |
| Transport to the API                             | TLS terminated at the Azure Container Apps ingress; `Strict-Transport-Security` for one year | Set by the application (`helmet`). The TLS minimum version is a first-deployment gate (task 11.12), owned by `010`.                                                                                                                                 |

## Notes

- `BETTER_AUTH_SECRET` is one key for cookie signing, TOTP secrets, backup
  codes, OAuth tokens and the `jwt` private key. That is a recorded residual
  risk (design, "Known residual risks").
- The key derivation for `symmetricEncrypt` is a single SHA-256 of the secret,
  which is acceptable only because the secret is a random string of at least 32
  characters, never a human-chosen password.
- Machine credentials are hashed with an unsalted fast hash on purpose: the
  input is a long random secret, so brute force and rainbow tables are not a
  practical attack. Passwords, which are low entropy, use `scrypt`.
