# Cryptographic inventory

SSA section SEC05, for `002-auth-and-rbac`. Every algorithm the system uses,
and where. It is read from the code and from the installed library sources
(`better-auth@1.7.6`, `@better-auth/api-key@1.7.6`, `@better-auth/utils@0.4.2`),
not from the design. Tayzu writes no cipher of its own: anything Better Auth
provides is used as configured, and the only primitives `@tayzu/auth` and
`apps/api` call from `node:crypto` are listed below. The keys and secrets
involved are in [Secrets](secrets.md).

## Notes

- `BETTER_AUTH_SECRET` is one key for cookie signing, TOTP secrets, backup
  codes, OAuth tokens and the `jwt` private key. That is a recorded residual
  risk (design, "Known residual risks").
- The key derivation for `symmetricEncrypt` is a single SHA-256 of the secret,
  which is acceptable only because the secret is a random string of at least 32
  characters, never a human-chosen password.
- Machine credentials are hashed with an unsalted fast hash on purpose: the
  input is a long random secret, so brute force and rainbow tables are not a
  practical attack. Passwords, which are low entropy, use `scrypt`.
- A completed password reset deletes the user's pending two-factor challenge
  rows (`2fa-<random>`) and `trust-device-*` rows by their `value`, which is the
  user id. The sibling `2fa-attempts-2fa-<random>` rows hold the value `0`, are
  not matched by that deletion, and expire with their challenge (10 minutes).
  They carry no secret.

## Exception: SHA-1 prefix of the breached-password query

`043` Resolved decision Q81, SSA section SEC05. A password is checked against
the Pwned Passwords range API, which is defined over SHA-1. This is an
exception to the rule against weak hashes, and it is accepted because:

- only the **first five hex characters** of the hash leave the system, so the
  service cannot tell which password was checked (k-anonymity), and the full
  hash and the password never leave;
- SHA-1 is **not used for storage or authentication**: passwords are stored with
  `scrypt` (above), and nothing verifies a password against a SHA-1;
- the range API **requires** SHA-1, so the algorithm is not ours to change.

If the range service is unreachable the check fails closed. The remaining
exposure is the egress itself to `api.pwnedpasswords.com`. The ticket
"Offline breached-password corpus" evaluates an offline corpus to remove it; it
is listed under "Tickets" in
[the design of change 043](../../openspec/changes/archive/2026-10-14-043-identity-lifecycle-and-org-admin/design.md),
with the ticket "FQDN egress allowlist" for `010`.
